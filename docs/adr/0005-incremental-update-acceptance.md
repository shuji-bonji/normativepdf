# ADR-0005: 増分更新の受入は「元バイト列の不変」と「他者が署名を検証できること」

- 状態: **Accepted**
- 日付: 2026-08-13
- 決定者: shuji

## 背景

増分更新（§7.5.6）は往復（ADR-0004）と受入の性質が違う。往復は「同じ**値**が返るか」
だったが、増分更新は「**元のバイト列が 1 ビットも動いていないか**」であり、
これは近似ではなく厳密に測れる。

条文がそう言っている:

> When updating a PDF file incrementally, changes shall be appended to the end
> of the file, **leaving its original contents intact**.（§7.5.6）

そしてなぜそれが要件なのかも書いてある:

> If a signed document is modified and saved by incremental update (see 7.5.6),
> **the data corresponding to the byte range of the original signature is
> preserved.** Therefore, if the signature is valid, the state of the document
> can be recreated as it existed at the time of signing.（§12.8.1 NOTE 1）

つまり増分更新の正しさは、**署名が生き残るかどうかで外から測れる**。これは
ADR-0004 が苦労して用意した「他者の目」が、ここでは仕様の側から与えられている
ということでもある。

## 決定

受入を 3 段で取る。**前段が緑でなければ後段は意味を持たない**ので、順序も固定する。

### 第 1 段: 元バイト列の完全一致（機械的・例外なし）

出力の先頭 N バイトが入力の N バイトと**完全に一致する**こと。N は入力の長さ。
1 バイトでも違えば失敗で、「ほぼ同じ」という結果は無い。

この検査は安いので**全経路で常に走らせる**。増分更新を名乗る関数が元を書き換えたら、
それは仕様違反であって設定の問題ではない。

### 第 2 段: チェーンが正しく読めること

- 追記後のファイルをパースすると、**新しい版のオブジェクトが返る**（§7.5.6:
  「最も新しいコピーが読まれるように相互参照情報を組み立てる」）
- **リビジョンが 1 つ増える**（`readXrefChain` のセクション数）
- 追記した trailer が `/Prev` で前のセクションを指し、**前の trailer の全エントリを
  引き継いでいる**（§7.5.6: 「Prev 以外の前 trailer の全エントリを持つ」）

### 第 3 段: 他者が読み、署名を検証できること

- `qpdf --check` が**元ファイルに無かった苦情を出さない**（ADR-0004 §2 と同じ形）
- **実署名検体に増分更新を掛け、pdf-verify-mcp の `verify_signatures` が
  VALID を維持する**（ROADMAP Phase 2 の受入そのもの）

第 3 段が本命である。第 1 段は「バイトが動いていない」しか言わず、
**動いていないバイトを間違った場所から数えている可能性**（例: origin > 0 の
ファイルでオフセットの原点を取り違える）は第 1 段では見えない。署名の
ByteRange は原点込みで定義されているので、そこで初めて露見する。

## 測らないと決めたこと

- **PDF/A 適合の維持は、いまは測らない。** 元が xref ストリームのファイルに古典
  テーブルを追記する形になるので、veraPDF の判定が動く可能性がある。§7.5.6 は
  追記するセクションの形式を縛っていないが、「縛っていない」と「実装が受け入れる」
  は別。**xref ストリームの書きが入ってから測る**（それまでは「未測定」と書く。
  緑とも赤とも書かない）
- **署名の付与は範囲外。** このライブラリは署名しない（DESIGN §1「作らない」）。
  測るのは「既にある署名を壊さないか」だけ。
