# ADR-0007: 文書モデルは「グラフ容器 + ページツリーの意味規定」までをライブラリに入れる

- 状態: **Accepted**
- 日付: 2026-08-14
- 決定者: shuji

## 背景

Phase 3（pdf-lib 撤去）の段取りを実測で立て直したとき、`pdf-writer-mcp/src` の
pdf-lib 依存 19 ファイルは **COS プリミティブが上位に来る**（`PDFName` 15 / `PDFArray` 10 /
`PDFDict` 9 / `PDFRef` 9）が、**難所は COS ではない**ことが分かった。難所は、それらが
生きた `PDFDocument.context` に対して register / lookup されることで、そこを置き換えるには
**文書（load → 編集 → save の器）が要る**。`handoff/phase3-pdflib-removal.md` §3.5 は
これを L2 として立て、「normativepdf には文書モデルがまだ無い。これが次に作るものである」と書いた。

**ところが [`../DESIGN.md`](../DESIGN.md) §5 は逆のことを言っている。**

> 低レベル一本でいく。**高レベル層（文書・ページ・ブロック）は MCP 側に置く。**
> writer が既に高レベルを自前化・封じ込めている現状が、そのまま答え

§6.1-5 も「高レベル層は…コアを崩さず**上に別パッケージとして**載せられる形を保つ」と続く。

つまり **「文書モデル」という語が 2 つの仕事をしていて、片方は §5 が作らないと言っている側**である。
どちらかが間違っているのではなく、語が粗い。実装に入る前にここを割る。

## 決定

### 1. 「文書モデル」を 3 つに割り、真ん中で切る

| # | 中身 | 帰属 | 根拠 |
|---|---|---|---|
| (a) | **グラフ容器** — load したバイト列の上に可変のオブジェクトグラフを置き、`writeFile` / `appendUpdate` に渡せる形にする | **normativepdf** | 直列化と対になる。§7.5 の住所 |
| (b) | **ページツリーの意味規定** — `/Count` 整合・重複参照の禁止・`/Parent` の維持・継承の解決 | **normativepdf** | 下記 §2。ISO が**書く側**に義務を課している |
| (c) | **オーサリング API** — `addPage` / `drawText` / ブロック配置・レイアウト | **writer**（作らない） | DESIGN §5。writer の `LayoutEngine` が既に持っている |

(c) を入れないので DESIGN §5 は**維持される**。§5 の言う「高レベル層」は (c) のことである、と読み方を固定する。

### 2. (b) をライブラリに入れる根拠は「shall の名宛人」である

好みではない。§7.7.3 の条文が**書く側を名指ししている**:

| 条文 | 何を要求しているか |
|---|---|
| **R-7.7.3.2-8** | 「**A PDF writer shall ensure** that the value of the Count key is consistent with the number of entries in the Kids array and its descendants」 |
| R-7.7.3.2-4 | ページツリーは同じ**ページツリーノード**への複数の間接参照を持ってはならない（shall not） |
| R-7.7.3.3-3 | ページツリーは同じ**ページオブジェクト**への複数の間接参照を持ってはならない（shall not） |
| R-7.7.3.3-5 | `/Parent` は Required かつ**間接参照でなければならない** |
| R-7.7.3.4-4 | 継承は**マージせず as-is**。配列・辞書のような複合型でも同じ |
| R-7.7.3.4-5/-6 | `/Resources` は Page から Parent を辿って探し、**最初に見つかった時点で探索を止め**、その辞書を**まるごと**使う |
| R-7.7.3.4-7/-8 | **Linearized なら継承してはならない** — 全属性をページ辞書に明示する |
| R-7.7.3.3-8 | リソースが不要でも `/Resources` の値は**空辞書**とする（省略ではない） |
| R-7.7.3.3-26 | **空の `/Contents` 配列を作ってはならない**（shall not） |
| R-7.7.3.3-28 | `/Rotate` は 90 の倍数 |

これらは「読む側が寛容に扱え」ではなく「**書く側がこう書け**」である。書く側が
normativepdf に移るのだから、義務も一緒に移る。ここを writer に残すと、
**将来の利用者が各自で同じ shall を実装し直す**ことになり、
`buildType0Font` が W-2 を表現不能にしたのと逆の状態（表現可能なまま各自が気をつける）に戻る。

⚠️ 一方 **R-7.7.3.2-2「PDF processors shall not be required to preserve the existing structure
of the page tree」**は、木を**組み直してよい**と言っているだけで、
**元の木を捨てたうえで別物にしてよい**とは言っていない。
増分更新は元の構造を保つ必要があるので、モデルの既定は**保持**とする。

### 3. 変更は上書きではなくオーバーレイ（copy-on-write）で持つ

`PdfDocument`（現状）は読み取り専用・遅延・キャッシュ付きである。そこに
**変更されたオブジェクトだけを載せる層**を重ねる。全オブジェクトを materialize しない。

**鍵は `objectNumber` + `generationNumber` の対**とする。番号だけにできない理由は下記の実測にある
（xref 全体では世代 ≠ 0 の in-use エントリが 2 検体・12 件に実在する）。

理由は 3 つあり、どれも既存の受入から来ている:

1. **`appendUpdate` は「何が変わったか」を入力に要求する**（`AppendUpdateInput.objects` =
   このリビジョンが書くオブジェクトだけ）。オーバーレイならその集合がそのまま取れる。
   全部を materialize すると**差集合を別途計算する**ことになり、計算を間違えれば
   増分更新に無関係なオブジェクトが混ざる
2. **ADR-0005 は「元バイト列の完全一致」を受入の第 1 段にしている。**
   オーバーレイは元バイト列に触れない
3. **遅延は性能ではなく到達性の問題である。** コーパスには 4MB 級の検体があり、
   `/Info` が存在しないオブジェクトを指す検体も実在する（段階 1 で踏んだ）。
   全件 materialize は、触ってもいないオブジェクトの解析失敗で load を落とす

### 4. 非同期のまま通す

`PdfDocument.getObject` / `resolve` は `Promise` を返す（オブジェクトストリームの遅延展開のため）。
**文書モデルもこれを隠さない。** 同期に見せるには全件先読みが要り、決定 3 と正面から衝突する。
writer 側の `editor.ts` は既に `async` の中にいるので、これで seam は成立する。

### 5. 受入 = 既存コーパスの往復が、文書モデル経由でも同じ結果になること

**L2 は新規実装なので、writer の `uc-oracle` は緑のまま動かない**（writer がまだ使わないから）。
**この段のあいだ、uc-oracle は何も測っていない。** それでも「終わった」と言えるようにするため、
受入は normativepdf 側で完結させる。

現在の往復の合格基準は `rewrite()` = `collectObjects` → `writeFile` の経路で測っている。これを
**文書モデル経由の「load → 無編集 save」に置き換えて**、同じ基準を適用する:

| 面 | 基準 | 出所 |
|---|---|---|
| 自己一貫性 | `npm run roundtrip:survey` が **2,881/2,881**（`corpus.lock.json` の `baselineRoundTrip`）を**下回らない** | ADR-0004 §2 |
| 他者可読性 | qpdf が**元ファイルに無い苦情を出さない**（同 2,881 件） | ADR-0004 §2 / GUARDS T-2 |
| 増分更新 | 実署名検体（`selfmade-pades-lta.pdf` / `dss-pades-5sigs-doctimestamp.pdf`）で **署名が VALID を維持** | ADR-0005 |
| 意味規定 | §2 の shall について **T-3 を実測する** — 検査を外したら通らなくなるテストがあること | GUARDS 第三部 |

**3 モード（`table` / `stream` / `objstm`）すべてで測る。** 段階 1 がそうしたから。

⚠️ **「往復が緑」だけでは受入としない**（ADR-0004 §1）。両側が同じパーサを共有するので、
読みの誤りと書きの誤りが打ち消し合う。qpdf の面が要る。

### 6. 意味規定は「検査」であって「修復」ではない

`/Count` が合っていない入力・重複参照を持つ入力は**実在する**（コーパスにある）。
モデルは**読むときは受け入れ、書くときに検査する**。

- **load は寛容** — 条文に反する木でも読める。読めなければ回復パースの後退になる
- **save は厳格** — §2 の shall に反する木は**書く前に投げる**。
  黙って直すと、利用者は自分が条文に反する木を作ったことを知らないままになる
- ただし **`/Count` だけは導出値なので再計算する**（R-7.7.3.2-8 が writer の義務と名指ししており、
  「呼び出し側が正しく数える」に賭ける理由が無い）。再計算した値が入力と違ったら**報告する**

### 7. 作らないもの（この ADR の範囲外と明記する）

- **オーサリング API**（(c)）— DESIGN §5 のまま writer に残す
- **ページの内容の解釈** — コンテンツストリームの再解析はしない。`ContentStreamBuilder` は書く側だけ
- **Linearized の生成** — R-7.7.3.4-7 は「Linearized なら継承するな」なので、
  モデルは**継承を解決できる**必要はあるが、線形化ファイルを作る必要は無い

## 測ってあること（2026-08-14・この ADR の時点）

- `src/` に文書モデルは無い。あるのは COS・パーサ・シリアライザ・増分更新・
  content / font / struct / conformance のビルダ（`src/index.ts` の公開表面で確認）
- `PdfDocument` は読み取り専用（`bytes` / `origin` / `headerVersion` / `version` / `trailer` /
  `xref` はすべて `readonly`、変更 API は無い）
- writer 側の `PDFDocument.load` の呼び出しは **`editor.ts:137` の 1 箇所**、
  `PDFDocument.create` は `builder.ts` と `page-ops.ts`。出口は `output.ts` の 3 関数
- `corpus.lock.json`: `specimens: 2907` / `baselineParsed: 2883` / `baselineRoundTrip: 2881`

### §6 の「厳格に投げる」は既存の検体を 1 つも落とさない（2026-08-14 実測）

「条文に反する木は実在する」は推定だったので、**決定する前に数えた**。
コーパス 2,907 件を `parsePdf` で開き、catalog → `/Pages` から木を歩いて数えた:

| 検査 | 該当 |
|---|---|
| `/Count` 不整合（宣言 ≠ 木を歩いた実測） | **0** |
| 同一ノード / ページへの重複間接参照（R-7.7.3.2-4 / R-7.7.3.3-3） | **0** |
| `/Parent` が間接参照でない（R-7.7.3.3-5） | **0** |
| 3 条件とも満たす | **2,889** |
| 読めない（既知・回復パースの分母外） | 18 |

**つまり §6 の「save は厳格」は、コーパス上でコストがゼロである。**
これを数えずに入れると「読めていた検体が書けなくなる」危険があったが、その危険は無い。

⚠️ 3 件とも 0 なので、**この 3 つの検査はコーパスでは一度も発火しない**。
実装するときは合成した検体で T-3 を取ること（コーパスは基準を下回らないことしか示さない）。

⚠️ **計器を先に T-3 に通した**（[[instrument-must-pass-t3]]）。0 件は「検査して 0」か
「検査が動かず 0」かを区別する必要がある。先頭 393 件で:

- 比較を 1 ずらす（`dv !== actual + 1`）→ **393/393 が挙がる** = 比較は生きている
- 同じ鍵を 2 回入れる → **393/393 で重複判定が発火** = 検出は生きている
- 歩いた結果は定数ではない（1 ページ 388 / 2 ページ 3 / **10,000 ページ 1** / 20 ページ 1）

### 継承・木の形・世代番号（2026-08-14 実測）

上の計測は根の `/Count` しか見ていなかったので、残り 3 件も数えた。

| 測ったこと | 結果 |
|---|---|
| 祖先から継承しているページ（§7.7.3.4） | **11 ページ / 11 検体**（`/Resources` 5・`/MediaBox` 5・`/CropBox` 5・`/Rotate` 0） |
| `/Resources` がページにも祖先にも無いページ | 0 |
| 中間ノード（根を除くページツリーノード） | **11 個**（ページ総数 12,932・木の最大深さ **3**） |
| そのうち `/Count` を持たないもの | **0** |
| ページツリー内の世代番号 ≠ 0 | **0**（木の中で見た間接参照 15,834 件すべて gen 0） |
| **xref 全体**の in-use で世代番号 ≠ 0 | **12 エントリ / 2 検体**（gen 1〜6 が各 2。`TWG test suite A029-pdfa2-pass-b/-d.pdf`） |

T-3（先頭 600 件で条件を反転）: 継承の判定を反転すると 10,614/10,614 ページが挙がる。
中間ノードの `/Count` を「持つ方」で数えると 11/11。世代の読み取りは 15,834 件すべてで値を返した。

**この 3 つが決めたこと**:

1. **継承の解決は実装する。** 11 検体で実際に使われている。ただし標本は狭く、
   11 件とも veraPDF の「6.1.13 Implementation limits」1 か所から来ている
2. 🔴 **オーバーレイの鍵は `objectNumber` だけにできない。** ページツリーだけを見ると
   世代 ≠ 0 は 0 件だが、**オーバーレイが鍵にするのは全オブジェクト**であり、
   そちらには 12 エントリ実在する。鍵は `objectNumber` + `generationNumber` の対にする
3. ⚠️ **木の形はコーパスでほとんど測れない。** 中間ノードが全体で 11 個・最大深さ 3 なので、
   2,889 検体の 99% は「根 → ページ」の平らな木である。木を組み直す実装を入れても、
   コーパスは後退を検出できない。合成した検体が要る

## 測っていないこと

- **文書モデル経由の往復が何件通るか** — まだ実装が無い。§5 の基準は「下回らない」であって、
  現時点の実測値ではない
- **世代 ≠ 0 のオブジェクトを実際に上書きしたときの挙動** — 実在する 2 検体は分かったが、
  そこに編集を掛けた結果は測っていない
