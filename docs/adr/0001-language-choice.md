# ADR-0001: 実装言語の選定

- 状態: **未決（Proposed）**
- 日付: 2026-07-20
- 決定者: shuji

## 背景

候補は **TypeScript** と **Rust（WebAssembly 出力を目的）**。

前提として、このライブラリの開発方式は
**「検証器を先に完成させ、その採点ループの中で実装を書く／生成させる」**（テスト駆動の極大版）。
言語選定はこの方式の成否に直結する。

## 選択肢

### A. TypeScript

**利点**

1. **戦う範囲を構造層に絞った時点で、Rust の主な利点が射程外になる。**
   Rust が効くのはシェイピング・フォントパーサ・暗号のホットスポットだが、
   そこは「当面戦わない」と決めた領域（[`../DESIGN.md`](../DESIGN.md)）。
   先行実装の実測でも Latin 1000 行 6.9ms / Unicode 1000 行 27ms（i3 mini-PC）で、
   文書生成に速度のボトルネックはない。

2. **生成コードを人間が査読できる。**
   この計画の要は、検証器で機械採点しつつ**最後に人間が目で見る**こと。
   実際、自 writer の W-2 は「pdf-lib が書いた辞書を自分の目で開いて」初めて見つかった。
   TypeScript なら shuji は条文と突き合わせながら読める。
   Rust では査読能力が追いつくまでの間 **veraPDF の緑だけが頼り**になり、
   検証器駆動への転落＝過適合リスクを自ら作ることになる。

3. **周辺インフラが全部 TypeScript。**
   4 MCP・Skill・フィクスチャ生成・テスト。境界を跨がない方が
   write → read-back → verify のループが速く回る。

4. shuji の主戦場（4 年以上）。

**欠点**

- JS ホスト以外への配布ができない
- 将来ホットスポットが問題化したときに書き直しが必要
- 数値処理・バイト操作の記述量が Rust より多い

### B. Rust → WebAssembly

**利点**

- JS 以外のホストにも配れる（Python / Go / ネイティブアプリ）
- フォントパーサ・暗号・大規模ファイルのストリーミングで性能優位
- 型システムと所有権がバイト列操作の安全性を担保する
- Rust の習得そのものが資産になる

**欠点**

- **査読能力が追いつくまで、生成コードを人間が検証できない**（利点 2 の裏返し）
- ビルド系の複雑化、JS ↔ WASM 境界のデータ受け渡し
  （バイト列は問題ないが、構造木のような構造化データが境界を頻繁に跨ぐとコストになる）
- **2 つの難しいことを同時に始める**ことになる（Rust 習得 + PDF エンジン実装）
- 「後で Rust に移植」は実務上ほぼ機能しない。**やるなら最初から**

## 判断材料

**当面の利用先はすべて JS ホスト**である。

| 利用先 | ホスト |
|---|---|
| `pdf-writer-mcp` の `pdf-lib` 置き換え | Node |
| Editor PWA | ブラウザ |
| e-shiwake の PDF 操作 | Node / ブラウザ |

したがって **WASM の主要な利点（JS 以外への配布）は、現時点で必要とされていない。**

## 推奨（未確定）

**TypeScript。**

理由の中核は性能ではなく **査読可能性**。
この計画は「LLM に正確に実装させる」ことを前提としており、
その安全装置は ①決定論的な機械採点（veraPDF）と ②人間の査読 の二重構成になっている。
Rust を選ぶと ② が当面機能せず、安全装置が片肺になる。

## 例外条項

**動機が「PDF エンジンを題材に Rust を習得すること」である場合、この推奨は当てはまらない。**

その場合は:
- **自動生成ではなく手で書く**
- 検証ループは学習の答え合わせとして使う
- 計画の性格（速度重視 → 習得重視）が変わることを明示する

これは十分に合理的な選択だが、**別の計画**として扱う。
