## 1. 看板 — 「作れる」ではなく「測ってある」

JS/TS 圏に、出力が veraPDF を通ることをリリースごとに示し続けているライブラリは存在しない
（2026-07-30 実測・2026-08-08 再確認）。そこが空席であり、そこに座る。

| 判定 | 文言 |
|---|---|
| ⭕ | **「出力が veraPDF を通ることを、リリースごとに証明している TypeScript の PDF ツールチェーン」** |
| ⭕（en） | *A TypeScript PDF toolchain that proves, release by release, that its output passes veraPDF.* |
| ❌ | 「pdf-lib の後継」— 席は `@cantoo/pdf-lib`（汎用）と `@pdfme/pdf-lib`（pdfme 専用）の 2 系統が埋めた |
| ❌ | 「タグ付き PDF を作れる唯一の TS 実装」— pdfkit があるので事実に反する |
| ❌ | 「TypeScript で PDF 2.0 対応」— バージョン番号に買い手はいない |

### 書ける / 書けない（主張の線引き）

| 書ける | 書けない |
|---|---|
| 「PDF/UA-1 の検証結果を出す」 | 「PDF/UA 準拠を保証する」 |
| 「veraPDF が COMPLIANT と判定した」 | 「ISO 19005 に適合している」 |
| 「EAA 対応の実務で使われる技術手段」 | 「法令が PDF/UA を要求している」 |
| 「器（署名・改ざん・形式）を検査する」 | 「文書の中身が正しいことを保証する」 |

この規律は verify の T1/T2/T3 区分と同じもの。**誇張しないことが差別化なので、守ることが利益になる。**

## 2. 競合の観測（監視リスト）

前提が変わったら §1 を書き直す。監視は事実ベースで安く回す。

| 対象 | 何が変わると効くか | 監視方法 |
|---|---|---|
| `@cantoo/pdf-lib` | PDF/A・タグ付けへの着手 | `npm view @cantoo/pdf-lib time.modified` + リリースノート |
| `@pdfme/pdf-lib` | 同上（現状は帳票用途の拡張のみ。HTML パーサ同梱） | `npm view @pdfme/pdf-lib time.modified` + `pdfme/pdfme` の packages/pdf-lib |

| Typst/krilla（Rust 圏） | JS 圏へのバインディング提供 | リリース監視 |

## 4. 公開チャネル

| チャネル | 現状 | 計画 |
|---|---|---|
| GitHub `shuji-bonji/normativepdf` | **README.md = 英語 / README.ja.md = 日本語へ転換済み（2026-08-11）** | 現在地（コーパス門番の数字）を README に載せ、更新時は実測値と同期する |
| npm `normativepdf` | **0.1.0 公開済み（2026-08-11・静かな公開 = 告知なし）。公開版検証 PASS**（31 エクスポート一致・実パース・/Version 格上げ動作） | 目的は名前確保 + reader/verify の依存解決のみ（プレースホルダでなく段階 0 の実体で確保）。**お披露目（告知・normativepdf.dev・veraPDF レポート同梱）は v1.0 で行う** = 看板「リリースごとに証明」が実演できるのは生成パス（Phase 3）以降のため |

## 5. 指標

| 指標 | 測り方 |
|---|---|
| **veraPDF 合格率** | リリースごとに記録。下がったらリリースしない |
| 週間 DL 数 | npm registry API（認知の唯一の客観指標） |
| コーパス通過率 | 段階 0〜1 の進捗指標 |

Star は指標に入れない（母数が小さく、露出依存で、自分の行動で動かせない）。

## 6. やらないこと

- 「もう 1 つの PDF ライブラリ」を名乗る — 補完に立つほうが全ライブラリのユーザーに届く
- pdf-lib 全機能の置換を目標にする — 278 issue が暗黙のスコープになる
- 検証できない主張を宣伝文に書く — §1 の線引きが正典
- Star を目標に置く
