# 設計方針

> 実装未着手。この文書は方針のプールであり、writer 完成後の 4 MCP 連携試験を経て確定させる。

---

## 1. 何を作り、何を作らないか

### 作る: 構造層

| 領域 | 理由 |
|---|---|
| オブジェクト構文・xref・trailer・増分更新 | `pdf-lib` が最も融通の効かない層。W-1 / F-3 がここ |
| フォント辞書（`FontFile` / `FontFile2` / `FontFile3`・サブセットタグ・`Length1`・CFF charset） | W-2〜4 の住所。**pdf-lib では直せない** |
| 構造木・タグ・`MarkInfo` | PDF/UA の本体。後付けにすると破綻する |
| XMP メタデータ・`OutputIntent`・catalog エントリ | F-4 / B-10 の住所 |
| AcroForm・注釈・添付 | 実務要件（電帳法・フォーム） |

### 作らない（当面）

| 領域 | 理由 |
|---|---|
| テキストシェイピング（GSUB/GPOS・BiDi・複雑文字体系） | **別ドメインの沼。** 先行実装はここを正しく実装しており（veraPDF 144/144）、勝負所ではない |
| ラスタライズ・レンダリング | 用途外 |
| OCR | family の射程外 |

> **重要**: 先行実装の失敗（F-1〜F-5）は**すべて構造層**で起きており、
> シェイピング層では起きていない。攻めるべき場所がここであることの傍証。

## 2. PDF 2.0 を基盤にする

ISO 14289-2 §6.2「Conforming files」:

> 「a file shall adhere to all requirements of **ISO 32000-2**;
>  a file shall adhere to all requirements of **ISO/TS 32005**」

**PDF/UA-2 は PDF 2.0 をハード要件とする。**
PDF 1.7 のみを基盤とする実装は、PDF/UA-2 に原理的に到達できない（先行実装がこの状態）。

TS 32005 が必要な理由は同 §6.2 NOTE 3 が説明している —
ISO 32000-2 Annex L は PDF 2.0 名前空間の containment rules しか持たないため、
1.7 名前空間の構造型を混在させるには TS 32005 が要る。

**両方ともコーパスに収録済み**なので、T1（条文で断定できる）のまま到達できる。

出力バージョンは用途で切り替える:

| 出力 | バージョン |
|---|---|
| PDF/UA-2 / 2.0 機能を使う | 2.0 |
| 互換重視・PDF/A 相当を狙う | 1.7 |

> `/ID` は ISO 32000-2 Table 15 で **PDF 2.0 では Required**（1.7 では任意）。

## 3. 主張と実体を乖離させない

[`GUARDS.md`](GUARDS.md) 第一部が本体。設計上の含意は 1 点:

**適合宣言を書く経路と、その要件を検査する経路を、同じ関数に閉じる。**

```
declareConformance(level) は
  requirements(level) を検査し
  満たさないなら宣言を書かずにエラーを返す
```

宣言を「メタデータを書く操作」として独立させると、
先行実装 F-1（フォント未埋め込みのまま PDF/A-2b を宣言）と同じ事故が起きる。

## 4. 検証可能性を設計に織り込む

### 4.1 決定論的出力

同じ入力から同じバイト列を出す。サブセットタグはフォントバイト列のハッシュ由来にするなど、
**時刻や乱数に依存しない**（自 writer の B-14 で採った方式）。

例外は `/ID`・作成日時・署名。これらは明示的に注入可能にする。

### 4.2 自前で検証器を持たない

**このライブラリは自己検証機能を持たない。** 検証は `pdf-verify-mcp`（veraPDF 委譲）に委ねる。

> 先行実装は自前 validator を同梱し、**フォント埋め込みを検査項目に持たなかったため
> 非適合ファイルを合格と判定した**。144 ルール中で唯一落ちた 1 個が自前検査の盲点と一致。
> **実装の盲点がそのまま検証の盲点になる。**

ライブラリが提供すべきは「検査結果」ではなく「**検査しやすい出力**」。

### 4.3 独立実装で読み戻せること

`qpdf --check` / `poppler` / veraPDF が読める出力であることを受け入れ基準にする
（[`GUARDS.md`](GUARDS.md) T-2）。

## 5. API の方向性（未確定）

検討事項のみ。確定は連携試験後。

- **低レベル（オブジェクト・辞書・ストリーム）と高レベル（文書・ページ・ブロック）を分離するか**
  → `pdf-writer-mcp` が必要とするのは低レベル寄り。高レベルは MCP 側に置く選択肢もある
- **ストリーミング出力**を最初から設計に入れるか（大規模文書・edge ランタイム）
- **パーサを持つか**
  → `pdf-reader-mcp` が既に pdfjs / pdf-lib で読んでいる。
    書きのための最小限の読み（増分更新の土台）は必要だが、抽出まではやらない
- **ツリーシェイク可能な ESM**（`sideEffects: false`）

## 6. family との関係

```
pdf-spec-mcp ──── 条文（設計の根拠）
                        │
                        ▼
                  ┌───────────┐
                  │ このライブラリ │ ← 構造層の実装
                  └───────────┘
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
  pdf-writer-mcp   Editor PWA      e-shiwake
        │
        ▼
  pdf-reader-mcp ──→ pdf-verify-mcp（veraPDF）
        読み戻し           機械採点
```

**共有基盤パッケージの候補**: ISO 条項番号・veraPDF ルール ID・適合レベルの対応表。
現在 family 内に散在している。houki family の `houki-abbreviations` に相当するものが PDF 側には無い。
**抽出の形は連携試験で決まる**（早すぎる抽出は避ける）。
