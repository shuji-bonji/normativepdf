# Proposal

## Why

ISO 32000-2 §7.9.2.2.1 は、テキスト文字列を UTF-16BE か UTF-8 で書くときの形（先頭のマーク）を定めていますが、形の壊れたバイト列（UTF-16BE の最後に 1 バイト余る、対になっていないサロゲート、UTF-8 として読めないバイト）をどう読むかは書いていません。UTF-16BE・UTF-8 の定義は Unicode Standard に委ねています。

`decodeTextString` は今、壊れたバイト列を 3 通りに扱っていて、どれもテストがありません（`text` の初版起こしで見つけた）。

| 壊れ方 | 今の振る舞い | 根拠 |
| --- | --- | --- |
| UTF-16BE の最後に 1 バイト余る | U+FFFD を足す | `decodeUtf16Be` のコメント「壊れていることが見える形で返す」 |
| UTF-8 として読めないバイト | U+FFFD に置き換える | `TextDecoder('utf-8', { fatal: false })` の既定 |
| UTF-16BE の対になっていないサロゲート | **そのまま返す**（JavaScript の文字列に孤立したサロゲートが入る） | 決めた跡が無い |

3 つ目だけが「見える形で返す」と食い違います。孤立したサロゲートを含む文字列は、`TextEncoder` で UTF-8 にすると U+FFFD に変わり、JSON や画面に出したときに初めて壊れ方が変わります。読み手（pdf-reader-mcp など）が受け取った文字列と、表示された文字列が違うことになります。

## What Changes

- 壊れたバイト列の読み方を正本（`text` の 012）に書く: 3 つとも、壊れた箇所を U+FFFD にして返す。
- UTF-16BE の対になっていないサロゲートを、1 単位ずつ U+FFFD に置き換える。
- 3 つの壊れ方を受入テストで固定する。

### 変わる振る舞い

- `decodeTextString` が、UTF-16BE の対になっていないサロゲート（後ろに下位サロゲートの無い上位サロゲート、前に上位サロゲートの無い下位サロゲート）を U+FFFD にする。

### 変わらない振る舞い

- 形の正しい UTF-16BE・UTF-8・PDFDocEncoding の読み方（001〜008）。補助文字のサロゲートペアは 1 文字として読む（004）。
- UTF-16BE の最後に余った 1 バイトの U+FFFD、壊れた UTF-8 の U+FFFD（今の振る舞いを固定するだけ）。
- 言語のエスケープ列の取り除き（005）。U+FFFD への置き換えの後に取り除く順序も変えない。
- 公開 API（`src/index.ts` の export）。

### 対象外

- 書く側（`encodeTextString`）に孤立したサロゲートを含む文字列を渡したときの扱い。今は UTF-16BE の形の壊れたバイト列を書く。別の変更で決める。
- PDFDocEncoding の文字列（1 バイト 1 文字で、壊れ方が無い）。

## Capabilities

- `text`（既存）: 012 を ADDED。

## 人が判断すること

- 孤立したサロゲートを U+FFFD にすること（2026-11-02 に選択済み。今の振る舞いをそのまま固定する案は採らない）。
- 版。読む側の出力が変わるので minor（0.10.0）か patch（0.9.1）。出力が変わるのは形の壊れた入力だけなので patch を提案。
